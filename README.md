# GoldAtom/0

**An experimental verifier-first prototype for Proof-Buried Work.**

GoldAtom/0 combines three distinct things that are often collapsed into the phrase “proof of work”:

1. **Exclusive local work** — a Bit-Gold-style SHA-256d proof bound to one pre-existing claim.
2. **Public historical burial** — Bitcoin fixes the claim, future challenge, mint order, and subsequent chainwork.
3. **Single-use title** — one Bitcoin UTXO carries the atom’s current ownership state.

The result is not a new blockchain and not yet a currency. It is a portable proof object that a verifier can independently accept or reject against a Bitcoin Core node.

> A GoldAtom is a Bit-Gold-style computational proof bound to a pre-existing Bitcoin claim, derived from an unknowable future Bitcoin challenge, committed back into Bitcoin, buried beneath subsequent chainwork, and transferred through a single-use Bitcoin title seal.

## Status

**Research prototype. Regtest and simulation only. No mainnet profile exists. Do not use real funds.**

The complete lifecycle passed repeated live Linux regtests on 2026-09-02 using Bitcoin Core `v31.99.0-031175197f1b` (source commit `031175197f1b7f90397b838a381f0892a74ca62a`). Release `0.0.3` adds an isolated one-command validation runner and an independent Node.js recomputation of every pure protocol commitment. The exact deterministic Bitcoin Core 31.1 release binary and macOS remain separate validation targets.

Version zero tests the narrower question:

> Can a compact proof bundle establish non-reusable local work, prior publication under Bitcoin, bounded mint timing, and current title without launching another consensus blockchain?

It does **not** yet solve monetary issuance, fair distribution, fungibility, price formation, privacy, or the choice of a production work function.

## What is implemented

- Canonical byte encodings and strict duplicate-key/unknown-field rejection for claim, challenge, work, mint, atom ID, and title transfers.
- A fixed **80-byte SHA-256d local-work header**.
- Future-block challenge derivation from canonical Bitcoin history.
- One-claim/one-mint enforcement through a spent claim UTXO and exactly one mint marker.
- A bounded mint window, preventing indefinite stockpiling of old challenges.
- Bitcoin transaction inclusion checks through `gettxoutproof` / `verifytxoutproof`.
- Canonical-height and reorganization checks.
- Dynamic burial assay using Bitcoin Core’s cumulative `chainwork` field.
- Client-validated title transfers using P2WPKH, P2WSH, or P2TR successor UTXOs.
- Terminal UTXO confirmation, script, and value consistency checks.
- A deterministic simulation fixture and portable JSON test vectors.
- Thirty-one deterministic and adversarial unit tests, including JSON-RPC protocol handling and economic-model invariants.
- A regtest lifecycle driver written against the Bitcoin Core 31 RPC surface.
- Preserved live regtest proof bundles, Core-backed verification, independent Node.js commitment recomputation, reversible reorganization tests, and exact execution transcripts.
- Deterministic stress models for work-weighted bullion, sealed epoch auctions, and proof-intersection gating.
- A non-normative `GoldAtom/1` canonical-vein-auction candidate derived from the disconfirming simulation results.

## What is deliberately not implemented

- A mainnet or signet profile.
- A ticker, premine, token allocation, or issuance schedule.
- Adaptive difficulty.
- A network service or peer-to-peer mempool.
- Smart contracts, a sidechain, or a new fork-choice rule.
- Claims that the proof measures literal electricity consumed. A valid below-target hash implies **expected statistical work**, not an audit of a miner’s utility bill.
- An assertion that Bitcoin burial work belongs exclusively to each atom. Bitcoin chainwork is shared historical security and is reported separately from local atom-specific work.

## Run the simulation

Python 3.11 or newer is sufficient; the package has no runtime dependencies.

```bash
cd goldatom-0.0.3
python3 -m goldatom simulate --output examples/genesis.goldatom.json
```

Expected shape:

```text
VALID GOLDATOM/0

Profile:                    goldatom-sim-v0
Atom ID:                    164b8c2f...
Expected local hashes:      16
Expected local work:        2^4.0000
Claim height:               100
Challenge height:           103
Mint height:                104
Bitcoin burial blocks:      1
Bitcoin burial chainwork:   10000
Title transfers:            0
Current title:              0c2dc53f...:0
```

The work target is intentionally trivial in simulation. Its purpose is to exercise the protocol, not create economic scarcity. Version zero also exposes only 64 variable work-counter bits per fixed claim; any production work-header requires a separately versioned rolling-search design.

To exercise a transfer:

```bash
python3 -m goldatom simulate \
  --with-transfer \
  --output examples/transferred.goldatom.json
```

## Run the adversarial tests

```bash
python3 -m unittest discover -s tests -v
```

The protocol suite currently checks:

- valid genesis atom;
- fixed 80-byte work-header vector;
- valid title transfer;
- tampered work hash;
- tampered nonce;
- challenge-block reorganization;
- target above the profile maximum;
- mint outside the allowed window;
- duplicate mint commitment;
- spent or missing title UTXO;
- broken transfer ancestry;
- relabelled transaction inclusion proof;
- duplicate JSON keys;
- noncanonical hexadecimal encodings;
- unsupported title-script templates;
- terminal UTXO value inconsistency;
- unconfirmed terminal title state;
- malformed nested JSON records.

The JSON-RPC tests additionally verify response IDs, malformed envelopes, authentication encoding, and preservation of Bitcoin Core error codes even when Core returns them inside HTTP 500 responses. The economic-model tests check concentration metrics, gate amplification, target granularity, checkpoint-censorship bounds, and the stated one-retry withholding threshold.

## Run the issuance stress models

```bash
python3 simulation/issuance_regimes.py \
  --json-output simulation/results/issuance-regimes.json \
  --markdown-output ISSUANCE-SIMULATION-0.md
```

The runner has no third-party dependencies and uses a fixed seed. Its figures are diagnostic toy models, not market forecasts or security proofs. The current result preserves work-weighted bullion as the control branch, rejects proof-intersection gating as a standalone minting rule, and recommends a claimant-independent **canonical vein auction** as the experimental GoldAtom/1 branch.

The resulting non-normative protocol candidate is in `SPEC-1-CANDIDATE.md`. Its core rule is that claimant-controlled bytes may compete to extract a vein but may never determine whether the vein exists.

## Recompute the portable commitments in Node.js

The independent checker imports no Python code and uses only Node.js built-ins:

```bash
node scripts/verify_vectors.mjs \
  examples/genesis.goldatom.json \
  examples/transferred.goldatom.json \
  examples/live-core-final-2026-09-02.goldatom.json
```

It recomputes claim, challenge, 80-byte work-header, SHA-256d work, mint, AtomID, and transfer commitments. It deliberately does not claim to verify Bitcoin transaction inclusion, active-chain membership, or UTXO state; those require the Core-backed verifier.

## Run against Bitcoin Core regtest

GoldAtom/0 is designed for a fully validating Bitcoin Core view. The adapter uses:

- `getblockchaininfo`
- `getblockhash`
- `getblockheader`
- `getrawtransaction`
- `gettxoutproof`
- `verifytxoutproof`
- `gettxout`

The lifecycle script additionally uses wallet and regtest RPCs to create and mine transactions.

Start a disposable regtest node. The exact executable location depends on your Bitcoin Core installation:

```bash
bitcoind \
  -regtest \
  -daemon \
  -server \
  -txindex=1 \
  -fallbackfee=0.0002
```

Then run:

```bash
python3 scripts/regtest_demo.py \
  --cookie-file "$HOME/.bitcoin/regtest/.cookie" \
  --output examples/regtest.goldatom.json
```

On macOS the cookie is commonly under the Bitcoin data directory in `~/Library/Application Support/Bitcoin/regtest/.cookie`; pass its actual path explicitly.

The script refuses to run unless Core reports `regtest`. It will:

1. Create or load a descriptor wallet.
2. Mine disposable regtest funds.
3. Publish a claim seal and `GA0C` commitment.
4. Mine forward to the predetermined challenge height.
5. Search the local 80-byte work-header space.
6. Spend the claim into one title output and one `GA0M` commitment.
7. Mine the mint plus a burial block.
8. Export a proof bundle.
9. Verify the exported bundle through the independent `CoreBitcoinView` path.

To re-verify an exported regtest bundle:

```bash
goldatom verify examples/regtest.goldatom.json \
  --cookie-file "$HOME/.bitcoin/regtest/.cookie"
```

For a fresh isolated end-to-end run—including independent Node.js recomputation, two semantic tamper tests, challenge-block invalidation, and restoration—use:

```bash
python3 scripts/run_live_core_validation.py \
  --bitcoind /path/to/bitcoind \
  --output-dir validation/live-core-local \
  --bundle examples/live-core-local.goldatom.json
```

The script starts a temporary isolated regtest node with inbound P2P listening disabled, records provenance and consensus primitives, removes the disposable datadir, and retains only the proof bundle and validation evidence.

The RPC adapter expects the historical claim and mint blocks to remain available. Supplying the block hash avoids requiring a global transaction lookup, but a heavily pruned node may still lack the old block data needed for `getrawtransaction` and `gettxoutproof`.

## Lifecycle at a glance

```text
claim tx at height h
  ├─ spendable claim-seal UTXO
  └─ OP_RETURN GA0C || claim_commitment
                  │
                  ▼
challenge block at h + Δ
  challenge = H(profile, claim outpoint, claim block,
                claim commitment, challenge block)
                  │
                  ▼
80-byte local header search
  SHA256d(GAW0 || challenge || claim_commitment ||
          extra_nonce || 00000000 || nonce) <= target
                  │
                  ▼
mint tx inside bounded window
  ├─ spends claim-seal UTXO
  ├─ creates title UTXO
  └─ OP_RETURN GA0M || mint_commitment
                  │
                  ▼
subsequent Bitcoin blocks bury mint
                  │
                  ▼
optional title transfer
  ├─ spends current title UTXO
  ├─ creates exactly one designated successor title
  └─ OP_RETURN GA0T || transfer_commitment
```

## The key accounting distinction

For a target `T`, the successful local hash has expected work:

```text
E[hashes] = ceil(2^256 / (T + 1))
```

That expectation is **atom-specific** because the challenge is bound to one claim.

Bitcoin burial is computed separately:

```text
burial_chainwork = tip.chainwork - mint_block.chainwork
```

It is not added to local work and is not multiplied by the number of atoms. One Bitcoin block can bury many commitments at once; treating all of its chainwork as exclusive matter inside every commitment would counterfeit scarcity by accounting convention.

## Current design claim

The preserved and freshly repeated 2026-09-02 live runs confirm that GoldAtom/0 has a coherent **object layer** under the tested regtest conditions:

- the proof cannot be transplanted to another claim;
- the claim can be consumed only once;
- the mint must occur inside a public time window;
- ownership is represented by one live title outpoint;
- a verifier can deterministically reject malformed or reorganized histories.

It does not yet have a coherent **monetary layer**. The first adversarial issuance pass shows why: work-weighted bullion is compute-elastic; a fixed auction converges toward ordinary hashpower competition; and proof intersections do not independently create exclusive ownership. The next specification target is therefore a two-branch comparison between honest compute-elastic bullion and the claimant-independent canonical vein auction specified provisionally in `SPEC-1-CANDIDATE.md`.
